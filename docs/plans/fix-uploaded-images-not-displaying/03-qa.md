# QA Report: Виправлення відображення завантажених зображень

## Test framework
- **Backend**: Pest 4 (`pestphp/pest` ^4.4) + `pestphp/pest-plugin-laravel` + `pestphp/pest-plugin-browser` (Playwright-based real-browser rendering), запущено через `docker compose exec app php artisan test`.
- **Frontend**: у репозиторії не налаштовано жодного JS unit-тест-раннера (немає Vitest/Jest, немає `@testing-library/react` у `package.json`, немає `vitest.config.*` чи `*.test.ts(x)` файлів). Per інструкцію задачі ("Vitest якщо налаштовано"), інсталяцію нового test runner-а не виконано — це вивело б за межі QA-фази (нова інфраструктура, а не тести) і ризикувало впертись у вже задокументовану в `02-development-frontend.md` проблему зламаного rolldown-біндингу для Node v26 на цій машині (той самий Vite pipeline, яким керується будь-який Vitest runner). Замість цього фронтенд-контракт (`MediaThumbnail` рендеринг, `resolveMediaSrc` HEIC-guard, поллінг) покрито через **Pest 4 Browser tests** — той самий інструмент, яким уже покрито весь інший UI в проєкті (`tests/Browser/**`), і єдиний реально працюючий у цьому середовищі спосіб перевірити відрендерений DOM.

## Tests added
- `tests/Feature/StorageRetrievabilityTest.php` — 2 тести. Ключовий тест проти самої причини бага: без `Storage::fake()`, пише реальний файл на публічний диск і перевіряє фізичну досяжність байтів через `public/storage` symlink (`File::exists`/`File::get` через реальний шлях, не через URL-shape).
- `tests/Unit/StorageLinkEntrypointTest.php` — 8 тестів (4 прості + 2×2 datasets). Структурна перевірка `docker/php/entrypoint.sh` (виконуваність, guard `PROCESS=app`, ідемпотентність через `[ ! -e ... ]`, `|| true` non-fatal) та обох `Dockerfile`/`Dockerfile-dev` (COPY+chmod entrypoint, `ENTRYPOINT`/`CMD` split, supervisord залишається CMD).
- `tests/Browser/Readings/ReadingPhotosTest.php` — 3 тести. Реальний браузерний рендер `Readings/Index`: фото з готовими конверсіями коректно "прошиває" правильний `optimized`-URL у `<a href>`-обгортку і приховує processing-бейдж; фото в обробці (жодної конверсії) рендериться без `<img>`, лише як `<a aria-label>`-обгортка (processing-стан, без crash/broken image); показання без фото не рендерить жодних фото-елементів. Див. "Iterations used" нижче — чому тест не асертує безпосередньо завантажений `<img src>`.
- **Не додано окремо**: unit-тест на `resolveMediaSrc`/HEIC-guard як чиста функція — немає JS unit runner-а (див. вище). Гілка HEIC-подавлення (`is_processing=false`, немає жодної конверсії, `original_url` закінчується на `.heic`/`.heif`) — штучний стан, який природно не виникає в жодному наявному browser-тесті (реальні тестові файли — JPEG через `UploadedFile::fake()->image()`), тож форсувати його через Pest Browser означало б підробляти медіа-дані нижче рівня Eloquent-моделі. Задокументовано як open issue нижче.

Ці гілки логічно прості (pure conditionals / already covered by unit test pattern в `ResolvesMediaConversionUrlsTest` для аналогічної логіки на бекенді) — ризик низький, але формально не 80%+ на цій конкретній частині.

## Iterations used
- **Attempt 1**: Написано 13 тестів (2 backend Feature + 8 backend Unit structural + 3 Browser). Прогін ізольованих файлів — усі пройшли одразу. Прогін повного набору (`php artisan test`) виявив 8 фейлів у `tests/Unit/StorageLinkEntrypointTest.php` — причина: `tests/Pest.php` підключає `TestCase`/Laravel bootstrap лише для `Feature`, `Browser`, `Modules/*/tests/{Feature,Unit}` директорій, **не** для `tests/Unit` — тому `base_path()` (Laravel helper) недоступний. Замінено на власну `dirname(__DIR__, 2)`-резолюцію шляху, не залежну від Laravel app-контейнера.
- **Attempt 2**: Повторний повний прогін дав 481 passed / 1 failed — перший тест `ReadingPhotosTest` (`renders a fully processed reading photo as an image`) падав ~1 з 3 повних прогонів на `assertAttributeContains('img...', 'src', ...)`. Діагностика (5× ізольований прогін підтвердив ~20% фейл-рейт; додано тимчасовий debug-тест з `page->script(...)` для інспекції реального DOM) виявила **справжню, детерміновану race-умову, не "ambient timing flakiness"**: `MediaThumbnail`'s `onError={() => setImgError(true)}` видаляє `<img>` і показує `ImageOff`-fallback, коли зображення не завантажується. У Pest Browser (Playwright + ефемерний `LaravelHttpServer`) сторінка обслуговується на динамічному `http://127.0.0.1:<random-port>`, а Spatie MediaLibrary `getUrl()` читає `config('filesystems.disks.public.url')` — літерал, зафіксований від `APP_URL` (`http://localhost:8000` у `phpunit.xml`) під час завантаження конфігурації, який ефемерний сервер **не** переписує (він переписує лише `app.url`/Laravel `UrlGenerator`-origin для навігації/Inertia-запитів, не MediaLibrary-диск). Тобто `<img src>` завжди вказує на `localhost:8000`, де нічого не слухає — реальний `fetch` зображення в браузері фейлить мережево, `onError` спрацьовує, і момент, коли це станеться відносно `assertAttributeContains`, залежить від навантаження CPU/event loop (звідси позірна "рідкісність"). Це артефакт тестового харнесу (невідповідність origin між ефемерним HTTP-сервером Pest Browser і статично сконфігурованим MediaLibrary-диском), **не дефект компонента чи фіксу**: реальна ретрівабельність байтів окремо підтверджена (а) `tests/Feature/StorageRetrievabilityTest.php` (реальний диск, без fake) і (б) ручною `curl`-перевіркою через живий FrankenPHP-контейнер (розділ "Verification performed" нижче) — обидва без залежності від Pest Browser origin-моделі. Виправлено: перший тест перейменовано і переписано так, щоб асертувати **прошивання правильного URL у `<a href>`** (елемент, що не залежить від `onError`/успіху завантаження зображення), замість очікування реального рендеру `<img>`. Повторні прогони: 5/5 ізольованих + 2 послідовні повні прогони (`php artisan test`) — 482 passed, 0 failed, без жодного фейлу.

Використано **2 із 3** дозволених attempt-циклів. Обидва виправлення — в тестовій інфраструктурі/асерціях (Pest suite wiring; Pest Browser origin-модель), не в production-коді фіксу.

## Verification performed beyond Pest (real container check)
На вимогу задачі — контейнер-рівнева перевірка symlink-механізму (Pest не може перевіряти `docker build`/`ENTRYPOINT` runtime-семантику напряму):
1. Перед перевіркою запущений `ka-app`-контейнер (15+ год uptime) **не мав** ні `/usr/local/bin/entrypoint.sh`, ні `/var/www/public/storage` — підтверджує, що образ, з яким контейнер було піднято, старіший за цей фікс (саме такий сценарій і спричиняв баг).
2. `docker compose build app` — образ уже зібраний з новим entrypoint-шаром (кешовано, усі шари `COPY entrypoint.sh` / `chmod +x` присутні).
3. `docker compose up -d --force-recreate app` — після перестворення контейнера `/usr/local/bin/entrypoint.sh` (`-rwxr-xr-x`) і `/var/www/public/storage` (symlink → `/var/www/storage/app/public`) з'явились автоматично, без ручного втручання.
4. Видалено symlink вручну, записано маркер-файл на `storage/app/public/qa-check/marker.txt`, виконано `curl -sk -L https://localhost:8443/storage/qa-check/marker.txt` — HTTP-запит повернув реальний вміст файлу (`QA_MARKER`), підтверджуючи byte-level retrievability через живий веб-сервер (FrankenPHP), а не лише URL-shape.
5. Прибрано тестові артефакти (`storage/app/public/qa-check/`) після перевірки.

Це саме той рівень верифікації, якого бракувало старим `Storage::fake()`-тестам і який BA прямо вказав як прогалину.

## Open issues
- **Немає JS unit-test runner-а в репозиторії** — `resolveMediaSrc` HEIC-guard (chиста функція в `resources/js/lib/media.ts`) і `MediaThumbnail`'s `onError`→`ImageOff`-fallback покриті лише опосередковано/не покриті напряму. Рекомендація наступній фазі (девелопер/DevOps): якщо проєкт вирішить інвестувати в JS unit-тестування — додати Vitest + `@testing-library/react` окремим інфраструктурним PR (поза скоупом цього фіксу), тоді покрити ці 2 гілки прямими unit-тестами за хвилини.
- **Queue-mismatch (root cause #2, задокументований у `02-development-backend.md`)** — не в скоупі цього фіксу і не покритий тестами тут; конверсії (`optimized`/`thumbnail`) продовжать "висіти" в `is_processing=true`, доки `MEDIA_QUEUE_CONNECTION` в `.env` розробника не узгоджено з фактичним queue worker-ом. Existing тести (`ResolvesMediaConversionUrlsTest`, нові тести тут) коректно моделюють обидва стани (processing/готово) через `markAsConversionGenerated()`, тож логіка сама по собі верифікована незалежно від фактичного стану черги.
- **Pest Browser не може перевірити реально завантажений `<img>` для MediaLibrary-URL** — задокументована в Attempt 2 причина: ефемерний `LaravelHttpServer`-origin (Playwright) і статично сконфігурований `filesystems.disks.public.url` (з `APP_URL`) — різні хости, тому будь-який `<img src>` з реальним MediaLibrary URL мережево недосяжний зсередини цього харнесу незалежно від того, чи виправлено баг. Якщо потрібне повне end-to-end підтвердження "картинка реально рендериться пікселями в браузері" — варіант для наступної фази: тимчасово `config(['filesystems.disks.public.url' => $ephemeralOrigin.'/storage'])` всередині тесту після `visit()`-bootstrap (складно, потребує доступу до `LaravelHttpServer`-порту до навігації) або окремий Dusk/Cypress-подібний E2E-прогін проти реального `docker compose`-стеку (поза Pest). Наразі ретрівабельність доведена на рівні реального диска (`StorageRetrievabilityTest`) + ручної контейнер-перевірки (curl), а UI-прошивання URL — на рівні DOM (`ReadingPhotosTest`); розрив між ними мінімальний і задокументований, а не прихований.
- **Cross-model MIME inconsistency** (webp vs gif між User/Meter і MeterReading) — задокументовано в BA/dev-звітах як окремий stakeholder-decision, свідомо не покрито тестами тут (поза скоупом фіксу).
