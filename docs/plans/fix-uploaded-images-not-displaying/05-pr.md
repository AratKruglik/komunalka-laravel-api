# Pull Request: Fix uploaded images not displaying (avatar, meter & reading photos)

## Summary

Uploaded images — user avatars, meter photos and meter-reading photos — were not
displaying anywhere in the app. Root cause was infrastructure, not storage: originals
were being saved via medialibrary, but the `public/storage` symlink was never created
in any Docker bootstrap, so the web server returned 404 for every media byte. A second,
functional gap was that meter-reading photos were already returned by
`MeterReadingResource` but never rendered by any page. This PR creates the symlink at
container start and adds the missing UI for reading photos.

## What changed

### Backend / infra
- `docker/php/entrypoint.sh` (new) — idempotently runs `php artisan storage:link` for the
  `app` process (guarded by `PROCESS=app`), then `exec`s the original command. Fixes byte
  retrievability behind FrankenPHP/Octane, including dev volume-overlay case.
- `docker/php/Dockerfile`, `docker/php/Dockerfile-dev` — COPY + chmod the entrypoint into
  `/usr/local/bin/`, split monolithic `ENTRYPOINT` into `ENTRYPOINT` (script) + `CMD`
  (supervisord) so the pre-flight symlink step runs without changing signal semantics.

### Frontend
- `resources/js/Components/ui/MediaThumbnail.tsx` (new) — shared rectangular thumbnail:
  URL resolution, processing spinner, `ImageOff` fallback on load error, processing badge,
  optional `<a target="_blank" rel="noopener noreferrer">` wrapper.
- `resources/js/lib/media.ts` — HEIC/HEIF guard in `resolveMediaSrc` (returns `null` for
  unrenderable `.heic`/`.heif` fallbacks instead of a broken `<img>`).
- `resources/js/Pages/Readings/Index.tsx` — renders `reading.photos[]` (Story 3) via
  `MediaThumbnail` with auto start/stop polling on processing photos.
- `resources/js/Pages/Meters/Components/MeterCard.tsx` — retrofit onto `MediaThumbnail`.
- `resources/js/Components/ui/index.ts` — export `MediaThumbnail`.

### Tests
- `tests/Feature/StorageRetrievabilityTest.php` (new) — writes a real file to the public
  disk (no `Storage::fake()`) and asserts physical byte reachability through the symlink.
  Catches exactly the class of bug the old fake-disk tests missed.
- `tests/Unit/StorageLinkEntrypointTest.php` (new) — structural checks of `entrypoint.sh`
  and both Dockerfiles (guard, idempotency, non-fatal fallback, ENTRYPOINT/CMD split).
- `tests/Browser/Readings/ReadingPhotosTest.php` (new) — real browser render of reading
  photos: processed, processing, and no-photo states.
- `Modules/Shared/tests/Unit/Concerns/ResolvesMediaConversionUrlsTest.php` — updated.

### Database
No DB changes.

## Testing

- Framework: Pest 4 (Feature + Unit + Browser/Playwright).
- Full suite: 482 passing (2366 assertions), 0 failing, 0 skipped — includes 13 new tests.
- How to verify: recreate the app container (`docker compose up -d --force-recreate app`);
  `/var/www/public/storage` symlink is created automatically. The new
  `StorageRetrievabilityTest` verifies real byte reachability (not just URL shape), which
  the previous `Storage::fake()` tests silently passed through. Manual curl of
  `/storage/...` against the live FrankenPHP container returned real file contents.

## Security

- OWASP review: 0 Critical, 0 High, 1 Medium (documented, not fixed), 2 Info (no action).
- Medium — predictable media directory path enumeration: media is served from the `public`
  disk with sequential media-id directories and no per-file authorization at the web-server
  endpoint. The symlink activates reachability, so it is reported here. Kept at Medium
  because uploads retain the user's original filename (a second unguessable component) and
  the data is low-sensitivity. Real remediation (private disk + authenticated streaming, or
  UUID path/file namers across three models) is architectural and deferred as a follow-up —
  out of scope for a display bugfix.
